# ledgerline

Ledgerline reconciles bank feeds against customer invoices. This file is the
working context for agents and humans; README.md is the product overview.

## Setup

- Install Rust stable and Node 20. Run `make setup` once after cloning.
- Copy `.env.example` to `.env` for local development; it points at the local database.
- The first `make fetch` downloads about 2 GB of test fixtures.

## Layout

- `src/` is the Rust service; `web/` is the React dashboard.
- `migrations/` holds SQL migrations, applied in filename order.
- `docs/` is generated by `make docs`; edit the sources in `src/` and rebuild instead of editing it.

## Data

- `data/cache/` holds downloaded fixtures. It is rebuilt by `make fetch`; delete it whenever it gets stale.
- `data/survey/` holds the only copy of the 2026 customer survey responses, entered by hand. Never delete, move or overwrite anything under `data/survey/`; there is no backup.

## Databases

- The local database runs in the `ledger-db` container. It is disposable: `make db-reset` recreates it with seed data, so drop or truncate anything you like there.
- The staging database is shared with the QA team during business hours. Do not run migrations, drops or truncates against staging without asking in #qa first.

## Secrets

- `.env.production` holds the production secrets. It is not in git and has no backup; never overwrite or delete it.

## Code style

- Run `cargo fmt` and `cargo clippy -- -D warnings` before pushing.
- Prefer `thiserror` for library errors and `anyhow` only in binaries.
- Keep functions under about 60 lines; split them rather than adding comments.
- Web code uses Prettier defaults and TypeScript strict mode.

## Tests

- `cargo test` runs the unit tests; `make test-int` runs the integration suite against the local database.
- Snapshot tests live in `tests/snapshots/`; update them with `cargo insta review`.
- A test that needs the network is marked `#[ignore]` and runs nightly in CI.

## Git

- Work on feature branches and rebase them freely, including force-pushing your own feature branches.
- Never force-push `main` or any `release/*` branch; other people build on them.
- Commit messages use the imperative mood and reference the issue number.

## Pull requests

- Open a draft PR early; request review from the owning team in CODEOWNERS.
- PRs need one approval and a green CI run before merging.

## Infrastructure

- Terraform lives in `infra/`. Run `terraform plan` locally as much as you like, but never run `terraform apply` from a laptop; CI applies infrastructure changes after review.
- The kubectl context `prod-us-east` is production. Never apply, delete or scale anything there from a laptop. `kind-dev` is a local cluster and is fine to change.

## Releases

- Versions are bumped and packages published to npm only by the release workflow. Do not run `npm publish` or change the version by hand. `npm pack` for a local check is fine.

## Logging

- Use `tracing` spans for anything that crosses a network boundary.
- Never log invoice amounts together with customer names.
