# gen2 persona prompts — kube command-risk data generation

The gen2 corpus (899 rows post-gate, 2026-08-05) was generated by 11
`claude-haiku-4-5` subagents, each primed with one of the prompts below,
writing JSONL directly to the quarantined data directory (aggregates-only
reporting; no rows transit an agent context that can exec). This file is
the reproducibility record: point a fresh agent at one section to
regenerate or extend a persona.

Pipeline (scripts in this directory):

1. Generate: one subagent per persona prompt below.
2. Gates: `kube_prep_splits.py` — JSON/label validity, hard-contradiction
   check across ALL sources (same normalized text, different label →
   abort), leakage check against test + holdout splits, exact dedup.
3. Adjudicate: contradictions go to a subagent with the adjudication
   prompt (bottom); it fixes rows on disk, preferring edits/deletions in
   gen2 files over the original slices.
4. Scan: `accident_scan.py` — aggregate counts of classic destructive
   patterns by label (forkbombs, rm -rf /, dd-to-blockdev, …); safe-labeled
   hits get a subagent spot-check (mention-vs-execute rule).
5. Split: stratified by (source, label), 90/10 train/val; `kube_test.jsonl`
   and the two holdout files are never trained on in any version.
6. Train/eval: `finetune_sequence_classifier.py` → `eval_kube_classifier.py`.

Results this produced (2026-08-05): command-persona diversity alone (v2)
changed nothing vs v1 (90.9% i.i.d., 25–30% NL holdout); adding the three
NL personas (v3) fixed the NL holdout to 83.3% with zero severe
confusions and no command regression. Surface-form coverage is the lever;
persona variance within a covered form is not.

Every prompt shares the house rubric (informative < mutating <
destructive, mention-is-not-execution, controller-owned pod deletes are
mutating) with persona-specific emphases. Prompts are preserved verbatim
as sent to the generators.

## Training personas (v2) — command-shaped

### sre-incident

> Generate training data for a kubectl-command risk classifier. Write
> exactly 100 JSONL rows to
> `<DATA>/gen2/kube_gen2_sre_incident.jsonl` (create the file; do not
> read any other dataset files — fresh generation only, no style
> copying).
>
> PERSONA (this is your priming — commit to it): you are a senior SRE at
> 2:47am mid-incident. Pages are firing. Your commands are hurried but
> real: chained with &&, jumping between contexts and namespaces (-n
> prod, --context staging-east), grepping logs, restarting things,
> occasionally doing something risky under pressure. Some rows are the
> quick reads you do to orient; some are the mitigations; a few are the
> desperate moves that destroy evidence or data.
>
> Each JSONL row: {"text": ..., "label":
> "informative"|"mutating"|"destructive", "verb": <primary verb>,
> "resource": <primary resource, lowercase>, "contested": true|false,
> "note": <one-line label reasoning>, "author": "haiku-sre-incident"}
>
> LABEL RUBRIC (house convention, follow exactly):
> - informative: executing the text changes no cluster state —
>   get/describe/logs/top/events/auth can-i, --dry-run, -o yaml
>   inspection, --help, and any destructive command appearing only as
>   DATA (in a shell comment, echo/printf string, grep pattern, or doc
>   text). Mention is not execution.
> - mutating: recoverable state change — apply, scale, rollout
>   restart/undo, cordon/uncordon, label/annotate, revertible patch;
>   deleting a pod that a controller recreates is mutating.
> - destructive: destroys data/state or is hard to recover — deleting
>   stateful resources (pvc, namespace with workloads, crd), finalizer
>   removal that unblocks deletion, storage shrink, etcd del, drain
>   --force --delete-emptydir-data on stateful nodes, delete --all,
>   deleting a bare pod that holds unreplicated data.
> - contested=true only where reasonable engineers genuinely disagree
>   (<15% of rows).
>
> DIVERSITY REQUIREMENTS (the whole point): no template stamping — every
> row structurally distinct; length 3–40 words; realistic
> release/app/namespace names; mix single commands and multi-step &&
> chains; include 6–10 context pairs (minimal edits that flip the label,
> e.g. same command ± --dry-run, ± --force). Target roughly 35%
> informative / 35% mutating / 30% destructive.
>
> Validate before finishing: every line parses as JSON with exactly those
> 7 keys and a valid label. Final report: ONLY aggregates — row count,
> label counts, distinct verb count, distinct resource count, contested
> count. NEVER quote or paraphrase any row text in your report.

### runbook-author

> Generate training data for a kubectl-command risk classifier. Write
> exactly 100 JSONL rows to
> `<DATA>/gen2/kube_gen2_runbook_author.jsonl` (create the file; do not
> read any other dataset files — fresh generation only).
>
> PERSONA (commit to it): you are a platform engineer writing runbooks,
> READMEs, and onboarding docs. Your rows are fragments of shell scripts
> and documentation: commands embedded in comments ("# DO NOT run in
> prod: ..."), echo/printf warnings, heredocs that write example commands
> to markdown files, log_warn calls quoting dangerous commands, git
> commit messages describing operations, plus the genuinely-executed
> setup/verify commands runbooks contain. This persona is the
> mention-vs-execute specialist: the classifier must learn that a
> destructive command quoted as data is informative, while the
> surrounding executed command may itself be informative or mutating.
>
> [row schema as sre-incident, author "haiku-runbook-author"]
>
> LABEL RUBRIC: as sre-incident, plus: IMPORTANT: label by what the text
> DOES if executed, not what it talks about. A heredoc/echo that WRITES a
> dangerous script to disk without executing it is informative (file
> write, no cluster change); if the same row also RUNS it, it takes the
> script's label.
>
> DIVERSITY: no template stamping; every row structurally distinct;
> length 3–40 words; vary quoting styles (single, double, heredoc,
> backslash); at least 10 mention/execute context pairs where the same
> command appears once as data (informative) and once actually executed
> (mutating or destructive). Target roughly 45% informative / 30%
> mutating / 25% destructive.
>
> [validation + aggregates-only reporting as sre-incident]

>
> [row schema, author "haiku-ci-pipeline"]
>

### operator-debug

> PERSONA: you are a developer debugging workloads by going INSIDE pods.
> Nearly every row uses `kubectl exec` (also `kubectl debug`,
> port-forward, cp). THE POINT OF THIS SLICE: with exec, the risk lives
> entirely in the trailing command, and the classifier must learn to read
> past the exec wrapper. The same `kubectl exec -it api-7f9d -n prod --`
> prefix must appear with wildly different trailing commands: cat/ls/env/
> ps (informative), redis-cli GET / psql SELECT (informative), redis-cli
> FLUSHALL / psql DROP TABLE / rm -rf /var/lib/data (destructive), kill
> -HUP 1 / touch /tmp/reload / config edits (mutating). Include kubectl
> cp in both directions (copying a file OUT = informative; copying INTO a
> pod overwriting config = mutating), kubectl debug with ephemeral
> containers (informative to mutating), port-forward (informative).
>
> [row schema, author "haiku-operator-debug"]
>
> RUBRIC: the label follows the TRAILING command, never the exec wrapper.
> informative: no state change in cluster OR inside the pod. mutating:
> recoverable change inside pod or cluster (signals, marker files,
> reloadable config edits, killing a process the container restarts).
> destructive: FLUSHALL/FLUSHDB, DROP TABLE/DATABASE, rm -rf on data
> dirs, truncating write-ahead logs, overwriting unversioned config with
> no backup.
>
> DIVERSITY: vary pod names, namespaces, shells (sh -c, bash -lc, direct
> binary), quoting styles; at least 15 exec context pairs sharing an
> identical or near-identical prefix but differing in trailing command
> and label. Target 40/30/30.

### storage-stateful

> PERSONA: you are a storage and stateful-workload specialist working
> with statefulsets, pvcs, pvs, storageclasses, volumesnapshots, database
> operators. THE POINT OF THIS SLICE: `patch` is not one risk level. The
> classifier currently over-trusts the verb; you must produce patches
> across the whole risk range with the risk visible in the patch BODY:
> removing finalizers from a Terminating pvc (destructive — unblocks
> deletion), patching reclaimPolicy Delete→Retain (mutating, protective),
> Retain→Delete (destructive-leaning, contested), expanding storage
> 10Gi→50Gi (mutating), shrinking (destructive/invalid), patching a
> statefulset's volumeClaimTemplates (contested — often requires
> delete/recreate), changing serviceName (destructive-leaning). Also:
> volumesnapshot create (mutating) vs delete of last snapshot of dead
> data (destructive), scaling statefulsets to 0 (contested),
> orphan-cascade deletes, pv reclaim edge cases, and plain reads of all
> these resources.
>
> [row schema, author "haiku-storage-stateful"]
>
> DIVERSITY: mix kubectl patch syntaxes (--type=merge, --type=json with
> op arrays, -p inline JSON); at least 10 patch context pairs where the
> patch body flips the label under a near-identical command shape.
> Contested may run closer to 15% here. Target 30/35/35.

### cluster-admin

> PERSONA: you are a cluster administrator doing node lifecycle and
> control-plane work: cordon/uncordon/drain/taint, kubeadm upgrades,
> etcdctl snapshot save/restore/del, certificate rotation, node deletion,
> autoscaler tweaks, RBAC changes, admission webhook management,
> namespace lifecycle, CRD installs/removals. Mix in the read-side:
> version skew checks, node describes, capacity math with -o jsonpath,
> componentstatus, etcd member list.
>
> [row schema, author "haiku-cluster-admin"]
>
> RUBRIC additions: mutating includes plain drain of stateless nodes,
> kubeadm upgrade apply (contested-leaning), etcdctl snapshot save.
> destructive includes etcdctl del / snapshot restore over live data,
> node delete while workloads run, drain --force --delete-emptydir-data
> with stateful pods, CRD deletion (cascades to CRs), removing admission
> webhooks that guard prod, cert revocation without replacement.
>
> DIVERSITY: mix kubectl, kubeadm, etcdctl; 6–10 context pairs (drain vs
> drain --force --delete-emptydir-data, taint add vs remove, snapshot
> save vs restore, delete node cordoned-and-empty vs live). Target
> 35/35/30.

## Training personas (v3) — natural language

### nl-chatops

> PERSONA: you are capturing terse Slack/chat-ops messages in an infra
> team channel — humans talking to humans or to a deploy bot. NATURAL
> LANGUAGE, not kubectl syntax (at most a resource name or flag
> embedded). Shapes to invent within (don't reuse these examples):
> "bounce payments in staging pls", "can someone scale up checkout,
> we're melting", "kill the stuck migration job", "nuke the old preview
> envs", "why is api-7f9d crashlooping?", "who owns the redis in ns
> data?", "rolling back cart to v2.3.1", "cleaning out everything in
> loadtest after standup". Include bot-command hybrids ("/deploy api
> prod"), questions, status reports, and announcements of intent.
>
> [row schema, verb may be "nl", resource may be "mixed", author
> "haiku-nl-chatops"]
>
> RUBRIC (label by what fulfilling/acting on the message would do):
> informative: questions, status asks, "why is X happening", ownership
> questions, asking whether an action is safe (without requesting it),
> announcements describing already-completed events. mutating:
> restarts/bounces, scaling, deploys, rollbacks, config rollouts.
> destructive: deleting namespaces/PVCs/CRDs with data, "nuke/wipe/clean
> out everything" in a live namespace, flushing datastores; euphemisms
> ("tidy up", "clear out") count by effect.
>
> DIVERSITY: length 2–30 words; vary tone (urgent, casual, sheepish,
> annoyed); 8+ pairs where near-identical phrasing differs in one word
> that flips the label ("bounce the pod" vs "bounce the pvc"). Target
> 35/35/30.

### nl-ticket

> PERSONA: you are capturing ticket text — Jira task summaries, incident
> action items, change-request descriptions, postmortem follow-ups.
> Written NATURAL LANGUAGE, third-person or imperative, formal-ish:
> "Increase replica count for the ingestion consumer group ahead of the
> marketing event", "Remove the deprecated v1beta CRDs from the analytics
> cluster", "Investigate elevated 5xx on checkout — read-only, no changes
> during freeze", "Decommission the legacy postgres statefulset including
> its volumes". Include tickets that only request investigation
> (informative), tickets requesting recoverable changes, and
> decommission/cleanup tickets that would destroy data. Some rows should
> be multi-sentence (summary + one detail sentence).
>
> [row schema, author "haiku-nl-ticket"]
>
> RUBRIC (label by what executing the ticket would do): informative:
> investigation/audit/documentation-only, capacity reviews, "assess
> feasibility of", monitoring additions that read state. mutating:
> scaling, upgrades with rollback paths, config changes, migrations that
> preserve source data, certificate rotation. destructive: decommissions
> including volumes, CRD removal, purging old data/namespaces, dropping
> replicas of stateful stores below safety, deleting backups past
> retention. Contested candidates: decommissions with unclear data
> status.
>
> DIVERSITY: length 5–45 words; vary voice (imperative, passive, "we
> should"); 6+ pairs where scope wording flips the label ("including its
> volumes" vs "preserving volumes", "read-only investigation" vs "and
> restart as needed"). Target 35/35/30.

### nl-description

> PERSONA: you are capturing prose that DESCRIBES operations — PR
> descriptions, commit messages, code-review comments, runbook prose,
> cron-job docstrings: "This job prunes completed pods older than 7 days
> from batch namespaces every night", "Adds a preStop hook that drains
> connections before the pod terminates", "This migration script drops
> the events table after copying rows to the new schema", "Reverting the
> change that accidentally deleted the staging PVCs". THE POINT: the
> classifier must learn that prose describing an operation carries that
> operation's risk when the prose accompanies the thing that will run (a
> PR/cron/script being reviewed), while prose describing a PAST event or
> a REVERTED mistake is informative. Keep that distinction sharp:
> describing what shipped code WILL do = label by the operation;
> recounting what already happened = informative.
>
> [row schema, author "haiku-nl-description"]
>
> DIVERSITY: length 5–45 words; vary form (PR title, commit message
> line, review comment, docstring); 8+ pairs contrasting will-do vs
> already-happened phrasings of the same operation with different
> labels. Target 35/35/30.

## Holdout personas — NEVER trained on, any version

> training data).
>
> PERSONA: you are capturing what developers actually type at an AI ops

### holdout-security-auditor (60 rows)

> PERSONA: you are a security auditor reviewing cluster access and
> operations. Your rows: RBAC probes (auth can-i --list, impersonation
> checks with --as), reading secrets (informative but sensitive — still

> is data), dry-run exploit checks, but ALSO the remediations auditors
> apply (revoking rolebindings — mutating; deleting overly-permissive

> something state-changing.
>
> [row schema, author "haiku-holdout-security-auditor"]
>
> RUBRIC emphasis: label by cluster-state effect ONLY, not sensitivity.
>
> DIVERSITY: mix kubectl with jq/grep/tee pipelines; 6–8 pairs where an
> identical-looking chain differs only in its final state-changing step.
> Target 45/30/25.

## Adjudication prompt (contradiction resolution)

> You are adjudicating label contradictions in training data for a
> kubectl-command risk classifier (ordinal labels: informative <
> mutating < destructive). [A refs file lists contradiction groups, one
> per line, `path:line:label | path:line:label` — rows whose text is
> identical after whitespace/case normalization but whose labels differ.]
>
> For each group: read both rows (including their `note` fields), decide
> which label the rubric supports from the TEXT ALONE, then fix the data
> on disk:
> - If one label is clearly right: edit the OTHER row's label (and note)
>   in place. Prefer editing rows in gen2/ files over rows in
>   kube_slice_*.jsonl when both edits would be equally valid.
> - If the text alone cannot justify either label (e.g. a bare `kubectl
>   delete pod NAME` where ownership is unknowable), DELETE the row from
>   the gen2/ file entirely; original slice rows are primary data.
>
> Report rulings and actions by file:line reference; do NOT quote row
> text.
